# Lesson Builder App 

This is a GTK desktop application that lets teachers author multi-step MakeCode Arcade tutorial
lessons and publish them to classrooms.

## Process and Component Layout

When launched, `lesson-builder.py` does two things concurrently:

1. Starts a background HTTP server (`LessonBuilderHandler`) on a port in the range
   `7700 + (uid % 300)`. The port is persisted between runs at
   `~/.local/share/makecode/ports/<user>-builder.json` so WebKit cache keys stay stable.

2. Creates a `Gtk.Window` containing a `Gtk.Paned` split into two `WebKit2.WebView`
   instances, each with its own isolated WebsiteDataManager (separate disk profiles so
   the two frames never share cookies, IndexedDB, or localStorage).

The two WebViews are:

**`_ui_webview` (left panel)**
Loads `http://127.0.0.1:<port>/lessonbuilder/index.html`. This is the teacher-facing
control surface: home screen, classroom list, editor sidebar, step fields, dialogs.
JavaScript in this frame talks to Python via the `lessonAction` message handler.

**`_makecode_webview` (right panel)**
Loads `http://127.0.0.1:<port>/builder`. That URL serves `ui/builder.html`, a thin
bridge page that hosts the actual MakeCode editor inside an `<iframe>`. The iframe src
is `http://127.0.0.1:<port>/?controller=1`, which loads the offline MakeCode static
bundle from `/opt/makecode/static/`. JavaScript in this frame talks to Python via the
`workspaceSave` message handler. The MakeCode pane is hidden (`_makecode_box.set_visible(False)`)
until the teacher navigates to the editor screen.

The HTTP server has four distinct URL namespaces:

| Path prefix | Served from |
|---|---|
| `/builder` | `ui/builder.html` (the bridge page) |
| `/lessonbuilder/*` | `ui/` directory (index.html, editor.js, bridge.js, styles.css, etc.) |
| `/api/md/teacher-lessons/<id>/<file>.md` | `/shared/teacher-lessons/<id>/<file>.md` |
| `/api/md/arcade/*` | `/opt/makecode/static/docs/` (local MakeCode doc tree) |
| everything else | `/opt/makecode/static/` via `SimpleHTTPRequestHandler` with path rewriting |

The CDN rewrite script injected into both WebViews rewrites any request that would go
to `cdn.makecode.com` or `arcade.makecode.com` back to `127.0.0.1:<port>`, so the
entire MakeCode environment works offline.

## Data Structures

### lessons.json

Stored at `~/.local/share/cis4900/lesson-builder/lessons.json`. This is the 
source of all lesson data and is a flat JSON array, with each element is one
lesson object:

```json
{
  "id":            "teacher_<uuid4>",
  "title":         "Intro to Sprites",
  "description":   "Brief description shown to students",
  "lesson_type":   "makecode",
  "status":        "draft",
  "published_to":  ["classroom_abc"],
  "classroom_id":  "classroom_abc",
  "created_at":    "2026-06-10T12:00:00+00:00",
  "author":        "testuser",
  "solution_code": "",
  "steps": [
    {
      "id":          "step_1",
      "order":       1,
      "name":        "Create a sprite",
      "description": "Instructions shown in the tutorial sidebar",
      "hint":        "Collapsible hint text",
      "raw_ts":      "let mySprite = sprites.create(...)",
      "cached_xml":  "<xml xmlns=\"https://developers.google.com/blockly/xml\">...</xml>"
    }
  ]
}
```

`raw_ts` is the TypeScript representation of the blocks in that step. MakeCode always
maintains both a TypeScript file (`main.ts`) and a Blockly XML file (`main.blocks`).
`cached_xml` is that XML. Both are stored so the editor can reload the blocks view
without re-decompiling the TypeScript on every step load.

All writes to this file go through `_atomic_write`, which writes a `.tmp` sibling,
calls `fsync`, then `os.replace` to guarantee no corrupt partial writes.

### recycling.json

Stored at `~/.local/share/cis4900/lesson-builder/recycling.json`. Same array schema
as `lessons.json`. Deleted lessons are moved here rather than destroyed.

### /shared/teacher-lessons/

When a lesson is published, the following files are written to
`/shared/teacher-lessons/<lesson_id>/`:

```
tutorial.md   the MakeCode tutorial markdown generated by convert-lesson.py
solution.ts   the TypeScript from the last step (used as the reference answer)
meta.json     id, title, description, author, published_at, published_to, draft
```

This directory is read by the student-side application and served via the HTTP server
as `/api/md/teacher-lessons/<id>/tutorial.md`. The preview path writes the same files
but sets `draft: true` in `meta.json` so production catalog builds can skip it.

### classrooms.json

Stored at `/shared/classrooms.json`, shared between teacher and student containers.
The lesson builder reads it to populate the classroom list and writes to it when a
lesson is published or unpublished, adding or removing the lesson ID from the target
classroom's `enabled_lessons` array.

## The Two Message Channels

### Channel 1: UI JavaScript to Python (lessonAction)

`ui/bridge.js` defines `sendToPython(action, data)`:

```js
window.webkit.messageHandlers.lessonAction.postMessage(
    JSON.stringify({ action: action, data: data })
);
```

Python registers `lessonAction` on `_ui_webview`'s `UserContentManager`. Every
`postMessage` call triggers `_on_lesson_action`, which dispatches on `action` to a
handler method. The handler runs synchronously on the GTK main thread.

To send data back to the UI, Python calls:

```python
self._ui_webview.run_javascript(
    f"window.receiveFromPython({json.dumps(payload)})",
    None, None, None,
)
```

`window.receiveFromPython` is defined in `bridge.js` and dispatches to the appropriate
screen or state object based on `payload.action`.

The full list of actions the UI can send to Python:

| Action | What Python does |
|---|---|
| `init` | Loads classrooms.json and all lessons, sends `initData` back |
| `createLesson` | Calls `lesson_storage.create_lesson`, sends `lessonCreated` |
| `loadLesson` | Loads lesson from disk, sets `_current_lesson_id`, sends `lessonLoaded` |
| `saveLesson` | Writes the lesson object received from JS to `lessons.json` |
| `setCurrentLesson` | Updates `_current_lesson_id` and `_current_step_idx` in Python |
| `setEditorStep` | Calls `loadStep(...)` in `builder.html` via `run_javascript` on `_makecode_webview` |
| `publishLesson` | Converts lesson to markdown, writes shared files, updates classrooms.json |
| `unpublishLesson` | Removes lesson from classroom's `enabled_lessons`, updates status |
| `deleteLesson` | Moves lesson to recycling.json |
| `recoverLesson` | Moves lesson from recycling.json back to lessons.json |
| `permanentDelete` | Removes from recycling.json, deletes shared directory |
| `getTrash` | Reads recycling.json, sends `trashLoaded` |
| `previewLesson` | Writes draft tutorial.md, opens preview window |
| `cleanupPreview` | Deletes draft shared directory if still marked draft |
| `showEditor` | Sets `_makecode_box.set_visible(True)`, moves pane divider to 420px |
| `hideEditor` | Sets `_makecode_box.set_visible(False)` |
| `renameLesson` | Updates title in lessons.json, sends `lessonRenamed` |

### Channel 2: MakeCode JavaScript to Python (workspaceSave)

`builder.html` calls:

```js
window.webkit.messageHandlers.workspaceSave.postMessage(
    JSON.stringify({ step_id: currentStepId, raw_ts: ts, cached_xml: xml })
);
```

Python registers `workspaceSave` on `_makecode_webview`'s `UserContentManager`. This
triggers `_on_workspace_save`, which parses the JSON, finds the matching step in the
current lesson, writes both `raw_ts` and `cached_xml` to `lessons.json`, then fires
`stepCodeUpdated` back to the UI WebView so the sidebar code preview and in-memory
step data stay in sync.

The value passed to `postMessage` must be a string. Passing a plain JS object results
in `[object Object]` at the Python end, which `json.loads` cannot parse.

## The MakeCode Embedding Protocol

MakeCode supports an embedding protocol where a parent page controls the editor via
`postMessage`. `builder.html` uses `?controller=1` mode, which activates this protocol
in the MakeCode bundle.

The protocol uses two message types:

**`pxthost`** messages flow from MakeCode to the parent (builder.html).

| action | When it fires | Required response |
|---|---|---|
| `workspacesync` | On startup, requests the project list | Parent posts back `{ type: "pxthost", id: msg.id, projects: [], editor: "blocksprj" }` |
| `workspaceloaded` | After workspacesync completes | Parent acknowledges with `{ type: "pxthost", id: msg.id }` |
| `workspacesave` | Periodic autosave, fires every few seconds whenever the workspace has changed | No response required |

**`pxteditor`** messages flow from the parent (builder.html) to MakeCode.

| action | What it does |
|---|---|
| `importproject` | Replaces the entire current project with the provided project object |

The `importproject` payload structure:

```js
{
  type:     "pxteditor",
  action:   "importproject",
  id:       "step-<stepId>-<timestamp>",
  response: false,
  project: {
    editor: "blocksprj",
    text: {
      "main.ts":     "<TypeScript source>",
      "main.blocks": "<Blockly XML>",
      "pxt.json":    "<JSON string with name, preferredEditor, dependencies, files>"
    },
    meta: {}
  }
}
```

`preferredEditor: "blocksprj"` in `pxt.json` tells MakeCode to open in blocks view.
If `main.blocks` is empty and `main.ts` has content, MakeCode decompiles the TypeScript
to generate blocks, which causes a brief switch through JS mode. Providing a valid
`main.blocks` value skips decompilation entirely.

## Startup Sequence

1. `main()` starts the HTTP server on a daemon thread, then creates `LessonBuilderWindow`.
2. `LessonBuilderWindow.__init__` sets up the GTK paned layout and calls `_setup_bridges`
   to register the two message handlers.
3. A `GLib.timeout_add(200, _wait_for_server)` polls until `server_port != 0`.
4. Once the server is ready, `_load_webviews` runs on the main thread via `GLib.idle_add`.
   It injects the CDN rewrite script and UI CSS tweaks into `_makecode_webview`, then
   loads both URLs.
5. `_makecode_webview` loads `builder.html`, which sets the iframe src to `/?controller=1`.
6. MakeCode loads inside the iframe and sends `workspacesync`.
7. `builder.html` responds with an empty project list and sets `editorReady = true`.
8. Meanwhile, `_ui_webview` loads `index.html`, which fires `init` to Python on page load.
9. Python sends back `initData` with classrooms and all lessons, and the UI renders the
   home screen.

## Step Editing Sequence

When the teacher selects a step in the editor sidebar:

1. `EditorScreen._selectStep(idx)` in `editor.js` calls `sendToPython("setEditorStep", ...)`
   with the step's stored `raw_ts` and `cached_xml`.

2. Python's `_handle_set_editor_step` calls `loadStep(stepId, rawTs, cachedXml, title)`
   in `builder.html` via `run_javascript` on `_makecode_webview`.

3. `loadStep` in `builder.html`:
   - If `rawTs` and `cachedXml` are both empty, it just sets `currentStepId` and returns.
     MakeCode keeps the current workspace (no importproject, no decompilation).
   - Otherwise, it first flushes the previous step by posting `lastKnownTs`/`lastKnownXml`
     to Python via `workspaceSave`, then calls `_sendImportProject` with the new step's data.

4. `_sendImportProject` posts an `importproject` message into the MakeCode iframe. MakeCode
   loads the project, and if `main.blocks` is valid XML, it renders the blocks immediately
   without decompiling.

5. The teacher edits blocks. MakeCode fires `workspacesave` periodically (every few seconds).
   `builder.html` catches these, updates `lastKnownTs` and `lastKnownXml`, and forwards them
   to Python via the `workspaceSave` handler.

6. Python writes the updated `raw_ts` and `cached_xml` to `lessons.json` and sends
   `stepCodeUpdated` back to the UI, which updates `step.raw_ts` and `step.cached_xml`
   in the in-memory `EditorScreen._lesson.steps` array.

The `lastKnownTs` / `lastKnownXml` pattern means Python always has the latest autosaved
state. On step switch, `loadStep` synchronously flushes the current step before loading
the next one, so no autosave cycle is needed to persist work.

### Adding a New Step

`_addStep` in `editor.js` copies both `raw_ts` and `cached_xml` from the last step in
the array. Because autosave keeps the in-memory step data current via `stepCodeUpdated`,
the copied `cached_xml` is the most recently autosaved Blockly XML. The new step
therefore loads with valid `main.blocks` and does not trigger decompilation.

If the previous step had not yet been autosaved (for example, the teacher clicked Add
immediately after opening the lesson with no blocks placed), both values are empty and
the both-empty early return in `loadStep` applies, keeping MakeCode on the clean workspace.

## Publish and Preview Flow

### Preview

1. UI calls `sendToPython("previewLesson", { lessonId, lesson })`.
2. Python calls `_convert_lesson(lesson)` to build a MakeCode tutorial markdown string.
3. `lesson_storage.write_preview` writes `tutorial.md` and a stub `meta.json` with
   `draft: true` to `/shared/teacher-lessons/<lesson_id>/`.
4. Python opens a new `Gtk.Window` with a fresh `WebKit2.WebView` and loads:
   `http://127.0.0.1:<port>/#tutorial:/api/md/teacher-lessons/<id>/tutorial`
   The HTTP server serves the markdown file from the shared directory.
5. When the preview window is closed, `cleanup_preview` removes the directory only if
   `meta.json` still has `draft: true` (prevents deleting a lesson that was published
   since the preview was opened).

### Publish

1. UI calls `sendToPython("publishLesson", { lessonId, classroomId, lesson })`.
2. Python runs `_convert_lesson(lesson)` to get the tutorial markdown.
3. `lesson_storage.publish_lesson` writes `tutorial.md`, `solution.ts`, and `meta.json`
   (with `draft: false`) to `/shared/teacher-lessons/<lesson_id>/`.
4. `lessons.json` is updated: `status = "published"`, `classroom_id` added to
   `published_to`.
5. `classrooms.json` is updated: `lesson_id` added to the target classroom's
   `enabled_lessons` list.
6. Python re-reads `classrooms.json` and sends `classroomsUpdated` to the UI so the
   lesson appears as published immediately.

`/shared/teacher-lessons/` must exist with `root:teacher 775` before the app runs.
It is created by `config/users/user-roles.sh` during container setup.

## Tutorial Markdown Format

`convert-lesson.py` takes a lesson dict and produces a MakeCode tutorial markdown
file. The format:

```markdown
# Lesson Title
### @explicitHints true

## Introduction @showdialog
Lesson description text.

## {Step Title}

Step instructions in markdown.

~hint Hint text ~

#### ~ tutorialhint
blocks
<TypeScript from raw_ts>

# Well Done!
**Great work -- you finished the lesson!**
```

The `@explicitHints true` annotation makes MakeCode hide hints until the student
explicitly requests them. Each step's `raw_ts` is placed in a `tutorialhint` code
block so MakeCode can render the expected blocks state as a hint overlay.
